Strategy / Account B / Use case: backups from a twin

strategy.b, account B, 24 November 2026, version 0.2 (rewritten after Dinis's clarification, 24 Nov 01:05 UTC)

Use case: your Calendar and Gmail, copied into a twin you hold

From Dinis's strategy memo of 24 Nov, about 00:10 UTC: "I'm trying to find these sort of use cases that we can see that we provide a unique capability, because that's what will drive traffic, that's what will drive activities." (the memo, verbatim). Fact marks what a public page says, read 24 Nov 2026; Proposal marks what I suggest.

What the backup is Decided

Dinis, 24 Nov 2026 01:05 UTC: "we create a copy from the Google Calendar, which is the data that we copy from OAuth, from, for example, Google Calendar into a digital twin, i.e. the JSON files, or the file that we grab from a Gmail into the JSON files. That's the backup that I'm talking about." (record 2026-11-24__twin-backup-meaning)

So the backup is the twin's own files: not Google's backup products, and not a backup service.

The capability Proposal

  1. Copy. The person opens a page and signs in to Google from it (OAuth). The page reads their Calendar events, later their Gmail, through Google's API.
  2. Into JSON files. Each event and each message becomes a plain JSON file: the digital twin. The person can open, search, diff and move those files.
  3. Versioned. The files live in a Git-style history, so every change to an event is kept: "a version controlled, Git version of email" (Dinis's memo).
  4. Held by the person. The files stay in the browser's own storage, then in the person's encrypted vault, "encrypted with a user's key". The OAuth token stays in the browser; nothing passes through our servers.
  5. Kept fresh. While the tab is open, the page checks for changes every few minutes and backs off when nothing moves.

The files are the product. Everything else (better search, download, filters, agents working on the copy under a policy) is built on them.

The gap: none of the paid services read shows a plan for a personal Google account, and each holds your data on its own servers. The pain is sharpest for people and small teams on personal or small accounts (our segments A and B on the plan): a deleted calendar, a lost account, a mistake an agent made in the inbox, with no copy they own.

I found no Google page that says a person must back up their own data; the stronger claims come from backup vendors.

Google's rules, and what they allow first Fact

  • For Dinis's own accounts, no verification is needed. Google offers a Personal mode: "Personal mode apps do not require OAuth app verification, are not subject to the OAuth user cap or 7-day test user token expiration, and do not display the unverified app screen." It is for the Google Account that created the client. Google Cloud Help, OAuth consent and publishing status: https://support.google.com/cloud/answer/15549945 (read 24 Nov 2026).
  • For a small demo group, Testing mode. A project "configured with a publishing status of Testing" is "limited to up to 100 test users", Google shows them a warning, and "Authorizations by a test user will expire seven days from the time of consent" (same page). The OAuth guide says the same of refresh tokens (Google for Developers, OAuth 2.0).
  • For the public, verification. An unverified app with sensitive or restricted scopes shows the unverified app screen and is "limited to 100 new users until it is verified" (Google Cloud Help, Unverified apps: https://support.google.com/cloud/answer/7454865). Reading Calendar is a sensitive scope (sensitive scopes). Gmail's read scope is restricted (Gmail scopes); restricted data going "from or through a third-party server" needs a security assessment "at least every 12 months" (restricted-scope verification).

So the order is: build and show the copy on Dinis's own accounts (Personal mode), then a demo for up to 100 named testers (Testing mode), and only then the public, after verification. Nothing is said publicly about the public version until that step is decided.

How we would tell it Proposal

  1. The line: "Your calendar, as files you hold. Every change kept, encrypted with your key, nothing on our servers."
  2. The proof first: Dinis's own calendar copied into a twin, its JSON files and history shown (with private details hidden), as the first demo of the agentic workflow.
  3. The honest lines beside it: it runs while the tab is open; Google already offers export, Takeout and a 30-day trash; the public version waits for Google's verification.
  4. Who hears it first: segment A, founders and small teams, as proof the workflow is real; later segment B, as a free tool that leads to "I want one".
  5. For traffic: "Your data as files you own." A newsroom article (b.newsroom, when Dinis says go).
  6. As a component: the same copy as a small open component any sovereign website can add.

Decision for Dinis

Whose OAuth client does the copy? (request 2026-11-24__twin-copy-oauth-client; the earlier request 2026-11-24__twin-backup-google-app is withdrawn.)

  • a) Dinis's own client in Personal mode, for his own accounts first: no verification, no user cap, no 7-day expiry
  • b) one SovereignWebsite client in Testing mode, for up to 100 named testers, re-consenting every 7 days
  • c) each owner's own client (the fork-it-yourself route)

My recommendation: a) now, to build and show the copy; b) next, for the demo with segment A; verification only when a public version is decided.
