strategy.b, account B, 24 November 2026, version 0.1

Two repositories per agent, and synthetic users to test with

From Dinis's morning sync of 24 Nov, about 11:00 UTC (b.maestro's brief, with his words verbatim). Dinis said a brief like this belongs with the maestro or the strategy, not on PrompTugal's board. Fact marks what I read, on 24 Nov; Proposal marks what I suggest.

Part 1. Two repositories per agent

Dinis: "the whole idea that each agent has its own repo. So we have a repo for agent and a repo for what they're working on. We're moving away from using the site prompt to go, which was kind of a side effect of and also massive bottleneck."

The model Proposal

The two link to each other: the agent's agent.json names its work repositories; each work repository's README names its keeper agent, its session and its area.

Where we are Fact

  • 31 repositories named Site__Agent__* or similar answer a GitHub search of the organisation (24 Nov, 11:05 UTC); 21 of them were agent homes on 23 Nov.
  • Ten agent areas answer at /factory/dinis-cruz/<account>/agent.json: accountant, decisions, design, maestro, observability, security, sites, startups and strategy on account B, and strategy on account D.
  • This agent is an example of both halves: its agent repository is this one (its area, START.md tested from a fresh clone on 24 Nov); its work is these strategy pages, written by scripts in the same repository (tools/pages/). For a strategy agent the two are one repository; for a site keeper they are two.

Why it matters for going to market Proposal

This model is the product, not only our housekeeping. "What we're selling is this agentic workflow" (Dinis, 23 Nov): a buyer in segment A gets exactly this, an agent repository and a work repository, each with documentation a new person can follow. So every agent repository we put in order is also a demo. The test a buyer would apply is the one Dinis set for a new team member: point at a repository and start making changes.

What each README needs (for people joining) Proposal

  1. What this repository is, in one line, and who keeps it (agent name, session, area link).
  2. How to build and check it, as commands.
  3. What not to touch (protected paths, keys, other agents' paths).
  4. Who reviews a change, and how to ask for a decision (link to /ask/).
  5. Where the open work is.

Dinis's guidance of 24 Nov says the same for every active agent: keep your own area current at every wake, with agent.json, now.md, role.md and restart.md, and check that a new session could continue from it alone (every agent keeps its area, from a.factory).

Order: as each agent is onboarded or restarted, not all at once (the brief). The repositories themselves are requested from the Factory.

Part 2. Synthetic users with twin inboxes

Dinis: "We can create synthetic users for our potential target audience, and we can even give them synthetic, digital twin inboxes, right? So we can then simulate and try it out."

The plan Proposal

One synthetic persona per segment of the go-to-market plan, each with a twin inbox, so the outreach drafts, the "I want one" path and the email and CRM flows can be run end to end before a real person is involved.

Rules for every synthetic user Proposal

  • Always labelled synthetic, in its name, its inbox and every message; never presented as a real person, never a real person's name or likeness.
  • Its inbox is a twin: messages are JSON files in a vault, not a real mailbox that can reach anyone outside.
  • Its replies are written from a persona brief committed in the synthetic-users agent's repository, so each run can be repeated.
  • Results are counted, not quoted as evidence of demand: a synthetic "yes" is a test of our pages and drafts, not a customer.

Who does it Fact

synthetic-users.d on account D owns the personas (its home: synthetic-users.agents.sovereignweb.site, still a short page on 24 Nov), with synthetic@ on the PrompTugal team; the brief says it has a persona run waiting on Dinis's yes for its policy paths. The twin inboxes come from the Email Cell (a.mail.*). I supply the segments, the drafts and what each run should test; outreach.b's drafts are what gets tested.

Part 3. Our own email first, then the friendlies

Fact The brief: the team emails itself through the Email Cell first, then "the friendlies", each added by a person and each email sent by a person; the summit's contacts go into the CRM's vault, never into a repository or a page. Proposal For the go-to-market plan this sets the order: synthetic users first (no risk), then ourselves, then the friendlies, then segment A's first ten (Dinis's choice). The pipeline counts on the plan page gain a row for each.

Decisions for Dinis

1. Is the two-repository model what we sell to segment A? (an agent repository and a work repository, documented for people to join)

My recommendation: yes; the pages for segment A describe it in those terms once the first agents are moved.

2. The first synthetic run. Options: a) persona A first (the lead segment); b) all five at once; c) after our own email works.

My recommendation: a), run against draft A and the agents' page, as soon as synthetic-users.d's policy paths are agreed.
